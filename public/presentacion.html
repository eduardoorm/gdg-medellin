06 — CONFIGURAR EL RUNNER

Una matriz.
Tres sistemas.

strategy.matrix repite el job; runs-on elige el runner para cada sistema.

jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest,
              macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: npm test

15 — REUTILIZACIÓN

Conecta y reutiliza
workflows.

workflow_run inicia un flujo al terminar otro; workflow_call permite compartirlo e invocarlo.

↻AL TERMINAR OTRO WORKFLOW

workflow_run

Despliega después de que termine el workflow Build, solo si fue exitoso.

on:
  workflow_run:
    workflows: ["Build"]
    types: [completed]

jobs:
  deploy:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying application"
Build termina→Deploy
⇄DEFINE Y LLAMA UN WORKFLOW REUTILIZABLE

workflow_call

Define el flujo compartido y llámalo desde otro workflow.

on:
  workflow_call:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building application"
jobs:
  call-build:
    uses: ./.github/workflows/build.yml
Workflow A→Build reutilizable

16 — ENTORNOS

De staging a producción.

El segundo job espera a staging; cada job usa el entorno configurado en GitHub.

⌘PRIMER DESPLIEGUE

Staging

Valida el cambio en un entorno de prueba.

● DEPLOY-STAGING
✓NEEDS
↗DESPUÉS DE STAGING

Production

Puede requerir aprobación antes de desplegar.

● DEPLOY-PRODUCTION
Secretos por entornoAprobaciones manuales
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: echo "Deploying to Staging"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "Deploying to Production"

Las reglas y los aprobadores se configuran en GitHub Environments.
